# FrameStudio Engineering Loops — Primary-Source Research

Target repo: `C:\Users\jcarnero\dev\FrameStudio` (Next.js 16 / TypeScript, static-export app on GitHub Pages, product: an fal.ai image-generation front-end).

This report is grounded entirely in the repo contents as of the research date. All claims carry file/line citations.

## Overview

FrameStudio ships a home-grown, GitHub-Actions-native multi-agent SDLC pipeline living under `.agents/` and `.github/workflows/`. Five role-specific agents (**triager → planner → developer → reviewer**, plus a background **sentinel**) are driven by a single Python runner (`.agents/run_agent.py`) that calls an OpenAI-compatible LLM endpoint (config calls the provider `multiverse`, model `glm-5-2` — this is **not** Claude Code, the Claude Agent SDK, or `anthropics/claude-code-action`; it is a custom tool-calling loop against a third-party/self-hosted model, per `.agents/config.yml:1-9` and `.agents/llm/factory.py`). GitHub issue labels are the pipeline's state machine: each agent reads an issue, does its job, and flips a label, which in turn re-triggers a workflow for the next agent — a closed loop that continues (with a developer↔reviewer sub-loop) until the issue is merged, escalated to a human, or a budget/iteration cap is hit. A separate static Next.js page (`/loop`) renders metrics assembled by a Python script into a committed JSON file at build/deploy time; there is no live API, database, or server component behind it.

## How the loop actually works

The mechanism is a **label-driven state machine over GitHub issues/PRs**, not a scheduled agent re-invoking itself, and not a `loop()` function — the "loop" is the sequence of GitHub events each agent's own writes produce, chained through workflow triggers.

1. **Entry**: An issue is labeled `needs-triage` (manually, or by the daily sentinel — see step 6). `agent-dispatch.yml`'s `issues: labeled` trigger fires; the dispatch job maps `needs-triage → triager`, `triaged → planner`, `ready → developer` via `LABEL_TO_AGENT` (`agent-dispatch.yml:70-74`).
2. **Triager** (`.agents/agents/triager.md`) reads the issue and either labels it `triaged` (well-defined, safe, right-sized — criteria at lines 15-24) or `human-review` (vague/dangerous/no DoD — lines 31-39). It never touches code (line 47).
3. Adding the `triaged` label is itself a labeled event, so `agent-dispatch.yml` fires again and routes to **Planner** (`.agents/agents/planner.md`). The planner either asks clarifying questions (adds `needs-info`, planner.md:33-45), or produces one or more fully-specified `ready` sub-issues with Context/Plan/DoD/Non-goals/Files (lines 58-101), closing the original. A dependency chain is expressed as a literal `Depends on #N` line in a sub-issue body; the dispatcher's `blocked_by_open_deps()` (`agent-dispatch.yml:84-92`) holds back dispatch of dependent issues until #N closes.
4. Labeling `ready` routes to **Developer** (`.agents/agents/developer.md`), the only agent allowed to write code (line 10). It creates branch `agents/issue-{N}`, implements the spec, runs `npm run build`/`npm run lint`, commits, opens a PR with `Closes #{N}`, and labels the issue `in-review` (workflow steps at developer.md:28-38). Developer tool access (`allowed_tools` in front-matter, developer.md:7) includes `write_file`, `commit_files`, `create_pr`, `run_command`, etc., defined and dispatched in `.agents/tools.py:359-705`.
5. Opening (or updating) that PR triggers `agent-review.yml` (`pull_request: [opened, synchronize]`), which runs the **Reviewer** (`.agents/agents/reviewer.md`). It diffs the PR against the linked issue's DoD, runs build/lint, and either `approve_pr` + `merge_pr` (closing the issue via "Closes #N"), or `request_changes` (reviewer.md:41-54). A `request_changes` review is itself a `pull_request_review: submitted` event with `state: changes_requested`, which `agent-review.yml`'s `if:` condition (lines 27-29) and its "Determine agent" step (lines 46-53) route back to the **Developer** — this is the actual self-correcting sub-loop: developer fixes → pushes to the same branch via `update_pr` → re-triggers `agent-review.yml`'s `synchronize` trigger → reviewer re-reviews. `.agents/config.yml:46-47` caps this at `developer_reviewer_max_cycles: 7`; `developer.md:69` separately states a hard cap of 5 iterations tracked in the developer's own working memory, after which it self-labels `human-review` + `failed-implementation` and stops (developer.md:69) — a discrepancy between the two stated caps (7 in config vs 5 in the prompt) worth flagging as a spec/implementation mismatch.
6. **Sentinel** (`.agents/agents/sentinel.md`) is the closest thing to a "scheduled loop": `agent-dispatch.yml`'s cron `'0 7 * * 1-5'` (weekday mornings) and the same `sweep()` function used for manual full-repo sweeps (`agent-dispatch.yml:128-157`) compute `pending_sentinel_missions()` (lines 94-126) — it diffs the current commit against the SHA recorded at each mission's (`bugs`/`tests`/`simplify`) last audit in `.agents/knowledge/sentinel-audits.json`, ignoring changes confined to `.agents/`, `.github/`, `public/` so the agents' own bookkeeping commits don't cause infinite self-triggering (comment at lines 94-99). If code actually changed, one pending mission is picked at random and run; the sentinel creates at most 2 `needs-triage` issues per run (sentinel.md:86) which then re-enter the pipeline at step 1. This is a deliberate anti-runaway-loop design: an unchanged codebase yields zero sentinel activity ("Stability first" section, sentinel.md:77-93).
7. **Cross-run continuity / anti-repetition**: Every agent invocation loads `.agents/memory/issue-{N}.md` (per-issue working memory, `run_agent.py:124-129,192`) and `.agents/knowledge/*.md` (project-wide knowledge, `run_agent.py:139-146,206`) into its context before acting, and every `finish()` tool call persists new memory (`run_agent.py:298-306`). If a run ends abnormally (budget/iteration exhaustion, empty-response streak) without calling `finish`, `save_progress_note()` (`run_agent.py:240-254`) auto-appends a "previous run ended: X, do not redo completed steps" note to memory so the next attempt doesn't repeat work — this is the mechanism that keeps the loop from looping forever on a stuck agent. Memory/metrics files are committed back to `main` by the "Commit memory" step (`agent-dispatch.yml:277-303`) via cherry-pick + retry (since concurrent matrixed agent jobs may push at the same time).
8. **Budget/safety limits**: per-agent `max_iterations` and `max_total_tokens` in `.agents/config.yml:13-34`; a deterministic "3 turns left" warning injected into the conversation (`run_agent.py:262-267`); and every non-`success` exit path calls `sys.exit(2)` (`run_agent.py:338-341`) so the GitHub Actions job shows red, which matters for the metrics collector distinguishing real successes from stuck runs.
9. **Downstream effects**: A developer's merge (via `merge_pr`, `.agents/tools.py:295-324`) pushes to `main`, which triggers both `version-bump.yml` (bumps patch version, pushes tag) and, because that push lands on `main`, `deploy.yml` (rebuild + redeploy + refresh metrics). `version-bump.yml`'s push is also to `main`, so it separately re-triggers `deploy.yml` again.

## Metrics dashboard architecture

**Data source → storage → web app → UI**, and explicitly, most of this is real and implemented (not spec-only):

- **Raw data source 1 — agent run telemetry**: every `run_agent.py` invocation appends one JSON line to `.agents/metrics/runs.jsonl` via `_write_metric()` (`run_agent.py:149-171`), recording timestamp, agent, issue, status, token counts (total/in/out), duration, iteration count, model, and mission. This file is checked into the repo and is itself committed by the "Commit memory" step of `agent-dispatch.yml` (line 284, `git add memory/ knowledge/ metrics/`).
- **Raw data source 2 — live GitHub API**: `.agents/scripts/collect-metrics.py` calls the GitHub REST API at *deploy build time* (not at page-request time) to pull all issues (`gh_get_paginated("/issues?state=all&filter=all")`, lines 38-53, 115) and compute label-based pipeline counts, bugs-found count, close-per-day histogram, and "sentinel" mission stats (`collect_issue_stats()`, lines 109-177).
- **Aggregation/derivation**: `compute_costs()` (lines 69-106) joins `runs.jsonl` records against `pricing` rates in `.agents/config.yml:36-40` (USD per 1M tokens, currently only priced for `glm-5-2`) to produce total/30-day/per-agent USD cost estimates.
- **Persistence hand-off**: `main()` (lines 180-206) writes one combined JSON — `runs`, `issues`, `costs`, `generated_at` — to **`public/loop-data.json`**. This is invoked as a build step in `deploy.yml:34-38` ("Collect metrics"), before `npm run build` (line 40) and the GitHub Pages artifact upload (lines 42-44). So the dashboard's data is a **static snapshot regenerated on every push to `main`**, not a live query, not a database (no Prisma/SQLite/Postgres anywhere in the repo — confirmed by `package.json` dependencies, which list only `next`, `react`, `react-dom`, `@fal-ai/client`).
- **Web app**: `src/app/loop/page.tsx` (a `"use client"` component) is the only consumer. On mount it `fetch`es `${base}/loop-data.json` relative to the current path (lines 583-593) — i.e., it reads the static file the build step wrote into `public/`, served as-is by GitHub Pages. There is **no API route** in this codebase at all (`src/app` contains only `page.tsx`, `layout.tsx`, `globals.css`, `favicon.ico`, and the `loop/` subtree — no `api/` directory), consistent with `next.config.ts:3-8` setting `output: "export"` (fully static site, no server runtime).
- **UI / metrics actually rendered** (all directly wired to `loop-data.json` fields, `page.tsx:579-753`): total runs with a 30-day sparkline, bugs found (+ open count), issues closed (of total), average run duration and total tokens, total/30-day USD cost ("Invested"), a 30-day stacked-bar daily-activity chart broken out by agent, a per-agent breakdown bar (run count + success rate), an issue-label "pipeline" funnel (needs-triage → triaged → needs-info → ready → in-review counts), a Sentinel-specific panel (findings vs. completed, broken out by mission: bug/test-coverage/simplification), and a recent-runs table (time, agent, issue, status, duration, tokens, cost). An `EmptyState` component (lines 564-575) is shown when there is no data yet.
- **What's not there**: no per-run cost breakdown beyond aggregate totals, no live/streaming updates (page only reflects the last `deploy.yml` run), no auth or write-back from the dashboard, and pricing table covers exactly one model — if the LLM config ever points at a different model without adding its price, `compute_costs()` silently falls back to `0` for that record's per-token cost (lines 82-92, "Legacy records only have a total" fallback also applies here).

## Root design docs — what they actually cover

`README.md` is the unmodified `create-next-app` boilerplate (no project-specific content). `AGENTS.md` (2 non-blank lines, `AGENTS.md:1-5`) only contains a warning that this Next.js version has breaking API changes from training data — it says nothing about the agent-loop system. `CLAUDE.md` is a one-line `@AGENTS.md` include. `SPEC.md`, `SPEC-v2.md`, `SPEC-v3.md`, and `SPEC-v3-feedback.md` are all **product feature specs for the image-generation app itself** (model wiring to fal.ai, seed handling, PNG metadata embedding, UI tab layout) — none of them describe the engineering-loop/agent system or the dashboard at all.

**Notable finding**: there is no root-level design document for the loop/dashboard system whatsoever. Its entire specification lives as code and as the individual agent prompt files under `.agents/agents/*.md` plus inline comments in `.agents/run_agent.py`, `.agents/config.yml`, and the workflow YAMLs. This is worth calling out explicitly per the task's instruction not to imply documentation exists where it doesn't — anyone onboarding to this system has to read the workflows and Python, not a spec.

## What could be reused/adapted for life-ledger

Observations only, no implementation proposed:

- **Label-as-state-machine pattern**: driving a multi-stage pipeline purely through GitHub issue/PR labels plus `workflow_dispatch`/`issues`/`pull_request` triggers avoids needing any external orchestrator or database — the entire pipeline state is visible in the GitHub UI.
- **Idempotent scheduled audits guarded by a content hash**: `pending_sentinel_missions()`'s "skip if code unchanged since last audit SHA, and don't count agent's own bookkeeping paths as code changes" pattern is a clean way to run a cron-triggered agent without runaway self-retriggering.
- **Auto-saved progress notes on abnormal exit**: `save_progress_note()` turning a raw tool-call log into a memory note prevents a stuck/budget-exceeded agent run from wasting the next run's budget re-discovering the same ground.
- **Static metrics snapshot instead of a live backend**: for a project already using static export (which life-ledger may or may not be), committing a JSON blob at build time and having a client component simply `fetch()` it is a zero-infrastructure way to get a metrics dashboard without a database or API route.
- **Explicit per-role tool allowlists and "you NEVER do X" rules in each agent's own prompt** (e.g., triager never touches code, developer is the only one who writes code, reviewer never approves without meeting DoD) is a lightweight but effective way to keep responsibilities separated when multiple agents share one codebase and one GitHub token surface.
- **Two different iteration caps for the same review/fix loop** (`config.yml:47` says 7, `developer.md:69` says 5) is a concrete cautionary example of prompt/config drift to watch for when a limit is expressed in two independent places.
