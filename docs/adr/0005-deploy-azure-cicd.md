# Deploy to Azure Container Apps via Bicep + GitHub Actions

Life Ledger is deployed to **Azure Container Apps** (ACA) in **West Europe**, provisioned by **Bicep** in `infra/` and shipped by **GitHub Actions**. Earlier ADRs settled the runtime shape (Go static binary on ACA, SQLite on a **replica-scoped ephemeral `EmptyDir` volume backed up to Azure Blob after each write and restored on boot** — [ADR-0003](0003-persistence-and-storage.md); in-app auth — [ADR-0004](0004-access-model-auth.md)) but explicitly deferred *deployment*. This ADR closes that gap. The end-to-end topology lives in [docs/architecture.md](../architecture.md); this records the decisions and the trade-offs behind them.

## Decisions

| Aspect | Decision |
| --- | --- |
| Compute | Azure Container Apps, West Europe, **min 1 / max 1** replicas (always warm). |
| Registry | **Azure Container Registry (Basic)**; the app pulls via a **managed identity** (AcrPull), no stored pull credential. *(Originally system-assigned; changed to a **user-assigned** identity — see [ADR-0006](0006-user-assigned-identity-for-acr-pull.md) — because system-assigned deadlocks the first deploy.)* |
| Infra as code | All resources in **Bicep** (`infra/main.bicep`), applied by a **separate** workflow (`infra.yml`) on manual dispatch or changes under `infra/`. |
| App deploy | **One gated workflow** (`ci-cd.yml`): a `test` job on **every PR and push to main**; a `deploy` job that `needs: test`, runs only on push-to-main, and only when **image-affecting files changed** (per-job gate — see below). Auto-deploys on push; no `workflow_dispatch` needed. |
| Deploy gate | A `changes` job runs a **`git diff` step** over the pushed range; `deploy` is gated on its `image` output. Docs-only/infra-only pushes run `test` but roll no revision. **Not** a whole-workflow `paths-ignore` skip (that would also skip `test`). |
| CI→Azure auth | **OIDC federated identity** (`azure/login@v2`) — no long-lived secret in GitHub. |
| Image tags | CD pushes `:latest` **and** `:<git-sha>`, then rolls the app onto the sha. Bicep pins `:latest`, so reapplying infra never reverts what CD deployed. |
| App secrets | `LIFELEDGER_PASSWORD_HASH` and `LIFELEDGER_SESSION_KEY` are GitHub Secrets, passed as `@secure()` Bicep params and stored as ACA secrets. |
| Secret-drift discipline | **Bicep is the single source of truth for env vars and ACA secrets.** CD only ever runs `az containerapp update --image ...` — never `--set-env-vars` / `--replace-env-vars` / `--secrets`. A CI guard fails if `ci-cd.yml` gains such a flag. |
| Timezone | Binary embeds tzdata (`import _ "time/tzdata"`); `TZ=Europe/Madrid` set in Bicep. |
| Rollback | ACA revisions. |

## Rationale / deviations worth recording

- **ACR Basic over GHCR, accepting ~$5/month.** The stack was chosen partly for a near-$0 cost (scale-to-zero free grant — see the stack research). ACR Basic and an always-warm replica consciously give that up in exchange for the cleanest Azure integration: managed-identity pull with **no registry credential stored anywhere**. GHCR would have been free but needs a GitHub PAT held as an ACA registry secret.
- **max 1 replica is not a tuning choice — it is a correctness constraint.** The SQLite database is single-writer ([ADR-0003](0003-persistence-and-storage.md)): one file on a replica-scoped ephemeral `EmptyDir` volume, backed up to a single Azure Blob path after each write. More than one replica would mean multiple replicas racing on that shared Blob path (last-writer-wins). The scale cap enforces the single-writer invariant the persistence design depends on.
- **min 1 (always warm) over scale-to-zero.** Scale-to-zero would restore the ~$0 story but adds a cold start on the first request after idle. For a personal app used in short bursts, always-warm was preferred for responsiveness. Revisit if cost matters more than latency.
- **Revision-swap window (known risk, not a blocker).** In single-revision mode a deploy briefly runs the old and new replica together while ACA hands over. With `EmptyDir` this is **not** two writers on one shared volume — each replica has its own local disk ([ADR-0003](0003-persistence-and-storage.md)); the exposure is that both back up to the **same Blob path**, so last-writer-wins can clobber a write made on the other replica in that window. At this app's write profile (one user, a handful of writes a day, deploys rare and operator-initiated) the odds of a write landing in that sub-second overlap are near-zero. The risk is **accepted**; the mitigation is operational (don't enter data mid-deploy), not architectural. NFS Azure Files removes the window entirely but was rejected on cost/complexity (ADR-0003). If write volume ever grows, graduate to a managed database rather than hardening around this.
- **Infra separate from app deploy.** Push-to-main ships the app fast (build image, roll revision); infra is a deliberate, reviewed act. Trade-off: after merging a Bicep change you must let `infra.yml` run (it auto-runs on `infra/**` changes, or dispatch it).
- **Per-job deploy gate over a whole-workflow path skip.** The obvious way to skip deploys for docs/infra-only pushes is `on: push: paths-ignore:` at the workflow level. Rejected: that skips the *entire* workflow, including `test`, so a docs-only PR leaves the required `test` check unreported and unable to merge under branch protection. Instead a `changes` job runs a `git diff` over the pushed range and `deploy` is gated on its output. `test` therefore runs on every PR and push; only the revision roll is conditional. The gate is `git diff`-based (dependency-free, transparent) rather than a marketplace path-filter action, matching the workflow's official-actions-only footprint. Ignore set: `**/*.md`, `docs/**`, `infra/**`, `.github/workflows/infra.yml`, `.agents/**`, `.claude/**`, `manual-process-samples/**` — a mixed code+doc push still deploys because code changed.
- **Bicep single source of truth; CD may only roll the image.** CD mutates the running app imperatively (`az containerapp update`), which is fine for the *image* (reconciled by the `:latest`+`:sha` convention above) but dangerous for anything Bicep declares. If CD ever ran `--set-env-vars`, `--replace-env-vars`, or `--secrets`, it would orphan the Bicep-declared env vars and the `password-hash`/`session-key` secret bindings — the next `infra.yml` apply would silently fight CD over them. So the discipline is: **CD only ever runs `az containerapp update --image ...`; all env vars and secrets change in `infra/` and are applied by `infra.yml`.** This is enforced by the pipeline, not by memory — a guard step in the `test` job fails if `ci-cd.yml` gains an env-/secret-mutating flag. (After a real image roll the `secretRef:` bindings and env vars are left untouched, so they survive intact.)
- **OIDC over a service-principal secret.** Federated identity means no long-lived credential to store or rotate. The three identifiers it needs (`AZURE_CLIENT_ID` / `AZURE_TENANT_ID` / `AZURE_SUBSCRIPTION_ID`) are not themselves sensitive but are kept as GitHub Secrets for uniformity.
- **`:latest` + `:sha` convention.** CD mutates the running image imperatively (`az containerapp update`), which would otherwise drift from the Bicep-declared image. Pinning Bicep to `:latest` — which CD always pushes alongside the sha — makes an infra reapply a no-op on the image, while the sha tag gives an auditable, rollback-able revision trail. Mild `:latest` smell, accepted for the drift-freedom.
- **tzdata embedded in the binary.** The server resolves "today" from the local wall clock; the distroless runtime ships no zoneinfo, so without the blank `time/tzdata` import a container would silently use UTC and file a late-evening expense under the wrong day. The import looks unused — **do not remove it.**
- **First-deploy bootstrap.** ACR is empty until CD runs, but the app can't be created pointing at a non-existent image. The first `infra.yml` run is given a public placeholder image (`mendhak/http-https-echo`, which needs no ACR pull and answers `/health` on `:8080`) via the `containerImage` input, so the placeholder revision reaches healthy in minutes on the *same* `/health:8080` probe production uses. CD then supersedes it with the real image; because the probe never changes, the swap stays healthy with no infra re-run. A health-serving placeholder is used deliberately rather than a probe concession — bending the probe to the placeholder would break across CD's image swap, relocating the readiness failure instead of removing it. Encapsulated in [`scripts/first-deploy.ps1`](../../scripts/first-deploy.ps1) and documented in [docs/deployment/first-deploy.md](../deployment/first-deploy.md). **Note:** the placeholder alone does *not* make the first deploy succeed — ACA still constructs the ACR pull secret for the configured registry at provision time, which deadlocked against the system-assigned identity's role grant. That is fixed by the user-assigned identity in [ADR-0006](0006-user-assigned-identity-for-acr-pull.md).

## Later upgrades left open

- Scale-to-zero if the cost of always-warm is not justified by usage.
- Azure Key Vault for the app secrets (instead of GitHub Secrets → Bicep params) if secret handling needs to move out of GitHub.
- Building the image in CI (not just at deploy) so a broken `Dockerfile` fails a PR rather than the deploy step.
